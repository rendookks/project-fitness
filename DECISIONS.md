# Decisions

1. **SDK 54 and iPhone remain the target.** Use the explicitly requested `default@sdk-54` scaffold and SDK-compatible packages, regardless of current Expo Go releases. The brief's App Store compatibility claim is time-sensitive; founders must verify their installed Expo Go supports SDK 54. No physical phone was inspected.
2. **Native Expo app, with web used for additional validation.** This is a local-first React Native prototype, not a hosted website. Browser checks supplement native export; they cannot establish phone compatibility.
3. **Repository-root application; preserve existing history.** The repository contained only a README. Scaffold in `/tmp` and transfer the required files while retaining `.git` and branch `work`.
4. **Use a writable npm cache.** The default home cache is unavailable in this sandbox. Cloud commands use `npm_config_cache=/tmp/project-fitness-npm`; ordinary laptop commands need no override.
5. **Small storage boundary and atomic session snapshots.** Store one JSON document per workout, with indexed status and timestamps, plus singleton profile/settings records. Nested exercises and sets are typed domain records. This avoids multi-table ordering errors and keeps each workout write atomic; SQL analytics are deferred. Migrations use `PRAGMA user_version` and never silently reset data.
6. **Local Manrope font assets, SIL Open Font License 1.1.** Bundle fonts from `@expo-google-fonts/manrope`; no network font request at runtime. Use system fallback if font loading fails. The trade-off is a slightly larger bundle.
7. **Writable Expo CLI state in Cloud.** The sandbox cannot create `~/.expo`. Build commands set Expo CLI's `__UNSAFE_EXPO_HOME_DIRECTORY` to `/tmp/project-fitness-expo` (a local CLI-state path, unrelated to application data). No runtime dependency or laptop setting is required.
8. **Real SQLite verification in addition to fakes.** A Node 24 `node:sqlite` driver runs the exact migration/adapter SQL on disk and reopens it. This catches SQL defects without claiming to execute the iOS native module. Browser validation uses Expo SQLite's WASM adapter; iPhone testing remains separate. Node 24 is the documented development baseline.
9. **Honor the Cloud network proxy for Doctor.** The initial Doctor attempt could not reach two online checks through direct Node fetch. Re-running with `NODE_USE_ENV_PROXY=1` and inherited proxy/CA settings passes all 18 checks; no checks are disabled and no TLS settings are weakened.
10. **One active workout; explicit set editor saves.** Session creation resumes an existing active session; duplicate exercise additions and finish operations are idempotent. Mutations are serialized and UI actions guarded while saving. Numeric edits stay in a modal until Save; dismissing them requires confirmation. This avoids writing invalid intermediate text and prevents unit-display rounding from modifying unchanged weights.
11. **Conservative input bounds and bodyweight treatment.** Accept 1–999 whole reps and 0–2,000,000 integer grams. Zero is allowed for all external loads (including bodyweight). Single-arm/per-side load is whatever the user records; no hidden doubling or inferred body mass. IDs combine local timestamp, a counter, and random suffix; they are record identities, not security tokens.
12. **Completion date defines training statistics.** Completed-at UTC instants are grouped by device-local Monday-start weeks. Incomplete sets remain visible in saved history but do not count. A session needs at least one completed set to finish; a warm-up-only saved session counts as a workout but contributes no working sets, records, or volume.
13. **SVG charts with accessible text summaries.** Use Expo-compatible `react-native-svg` for a target ring and a small line chart, plus native weekly bars. No heavy chart framework or animation dependency. The chart shows up to six qualifying sessions; complete exercise history stays visible below. No claim of muscle growth, readiness, or a measured frame rate.
14. **Rules only; informational future screens.** AI Coach opens a deterministic Rule-based Insights list with evidence and no chat input. Fuel, Learn, and Recovery disclose their preview status and only link to working features. No fictional health readings or implied integrations are displayed.
15. **No dependency on motion; keep device review explicit.** Meaningful state changes are immediate and persistence is never delayed for animation. This also respects reduced-motion preferences without an animation subsystem. Native keyboard, text scaling, VoiceOver, and final visual approval still require iPhone testing.

16. **Decimal-aware display rounding.** Use Intl formatting at two decimal places (half-expand, without modifying stored grams); editable numeric text uses ungrouped en-US decimal syntax regardless of display locale. This fixes binary `toFixed` edge cases such as 61.235 kg displaying as 61.23. Display remains approximate to 0.01 units; unchanged fields preserve the original exact grams.
17. **Separate demo database with explicit identity guards.** Real records use `project_fitness.db`; fictional records use `project_fitness_demo.db`. Each adapter has a checked kind, and seeding refuses the real database. The only demo-control value kept in real settings is the selected-mode preference; no fictional fitness records enter the real file.
18. **Schema v2 adds seed metadata without rewriting workouts.** A transactional, versioned migration adds a metadata table. An atomic seed transaction writes an idempotence marker last. Normal mode switches/restarts never reseed deleted or edited samples. Demo reset atomically replaces only the demo file’s records and restores sample history; real reset clears only real records and restarts onboarding.
19. **Deterministic, date-anchored fictional history.** Seed 11 completed sessions over four device-local Monday-start weeks, using stable IDs, a fictional profile, and integer-gram loads. Given the same input instant, records are identical. Dates are anchored on first enable, persisted thereafter, never future-dated, and refreshed only by an explicit demo reset. The trade-off is that an old demo eventually shows an inactive current week; it is never silently changed to appear current.
20. **Switch after destination validation.** Initialize/migrate/read the target database before persisting a mode change. Refresh the provider’s repository and snapshot together after success; guard UI actions during switching. Preserve unfinished sessions independently in both files. Show DEMO MODE globally and in editing/confirmation sheets. Units and onboarding profiles remain independent per database.

21. **Deliver the existing `work` branch without merging the default branch.** Preserve the initial commit and four sequential stage commits, then use a normal push with no force. The laptop clone command explicitly selects `work`; the trade-off is that founders must select or merge this branch before expecting the default branch to contain the app. No pull request or default-branch merge is required for this delivery.
